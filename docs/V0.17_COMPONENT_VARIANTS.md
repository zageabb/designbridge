# v0.17 Component variants and safe instance switching

DesignBridge v0.17 adds canonical component variant families and guarded switching of component instances.

## Canonical variant model

A component may define:

- `variant_group` — stable family ID;
- `variant_properties` — the property combination represented by that component.

Example:

```json
{
  "id": "button-primary",
  "type": "component",
  "name": "Button Primary",
  "variant_group": "button",
  "variant_properties": {
    "style": "primary",
    "state": "default"
  }
}
```

Duplicate property combinations inside the same variant group are rejected.

## Stable variant slots

Component variants cannot reuse DesignBridge node IDs because IDs are globally unique.

To preserve instance overrides across variants, corresponding component children can define a stable `variant_slot`.

Example:

```json
{
  "id": "button-primary-label",
  "type": "text",
  "name": "Label",
  "text": "Continue",
  "variant_slot": "label"
}
```

Another component in the same variant family can use a different node ID but the same slot:

```json
{
  "id": "button-secondary-label",
  "type": "text",
  "name": "Label",
  "text": "Continue",
  "variant_slot": "label"
}
```

An override on the source child can therefore be remapped safely to the target child.

## Variant family report

`GET /api/penpot/projects/{project_id}/variants`

The response reports:

- variant groups;
- component/property combinations in each group;
- stable slots exposed by each component;
- current variant-backed instances and their overrides.

## Compatibility planning

`POST /api/penpot/projects/{project_id}/variant-switch-plan`

Before Penpot changes anything, DesignBridge validates:

- source and target belong to the same variant group;
- the target is different from the current component;
- every overridden source child has a `variant_slot`;
- the target contains the same slot;
- the source and target slot types are compatible;
- text overrides still target text nodes;
- direct fill overrides are not remapped onto token-bound target nodes.

The plan returns:

- source/target components;
- source/target variant properties;
- compatibility issues;
- remapped target override IDs.

## Guarded switch transaction

The Penpot UI now includes **Review variants**.

A switch follows this sequence:

1. request a compatibility plan;
2. require Penpot's stored revision to match the plan revision;
3. use Penpot's native `swapComponent(...)` on the copy instance;
4. reapply the remapped safe overrides;
5. commit the canonical component ID and remapped override IDs to DesignBridge;
6. advance the Penpot revision only after the canonical commit succeeds.

If the final canonical commit fails because DesignBridge changed during the switch, the UI attempts to swap Penpot back to the original component and original canonical override set.

## Penpot behavior

DesignBridge uses Penpot's native component swapping rather than detaching/recreating the instance.

This keeps the instance as a component copy and allows Penpot to retain compatible overrides.

## Current boundary

v0.17 models variants canonically and switches between compatible component definitions.

It does not yet automatically create or reorganize Penpot VariantContainers from DesignBridge variant groups.

Native Penpot VariantContainer integration can follow once canonical grouping and safe switching have proven stable.

## Next milestone

The next useful slice is native Penpot variant-container integration:

- discover Penpot native variant groups/properties;
- map them to DesignBridge `variant_group` and `variant_properties`;
- use native `switchVariant(...)` when the family is represented as a Penpot variant;
- retain the current safe component-swap fallback for ordinary grouped components.
