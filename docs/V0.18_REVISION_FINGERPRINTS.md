# v0.18 Durable revision fingerprints

DesignBridge v0.18 hardens revision identity so a reused numeric revision cannot be mistaken for the same content.

## Problem

The revision store intentionally truncates redo history after undo followed by a new save.

That means this sequence is valid:

1. A = revision 1
2. B = revision 2
3. Penpot stores revision 2
4. DesignBridge undoes to revision 1
5. C is saved
6. C becomes revision 2

The numeric revision is the same, but B and C are different documents.

Before v0.18, stale Penpot state could therefore report itself as synchronized solely because both sides said revision 2.

## Revision token

Every stored revision now carries a deterministic SHA-256 fingerprint.

The fingerprint is generated from canonical DesignBridge JSON using:

- sorted object keys;
- compact JSON separators;
- UTF-8 encoding;
- fields normalized through the Pydantic DesignBridge model.

Conceptually:

```python
canonical = json.dumps(
    document.model_dump(mode="json", exclude_none=True),
    sort_keys=True,
    separators=(",", ":"),
    ensure_ascii=False,
)
revision_token = hashlib.sha256(canonical.encode("utf-8")).hexdigest()
```

The token identifies content, while the numeric revision still identifies the position in the current project history.

## Database migration

The `revisions` table now includes:

```text
revision_token TEXT
```

Existing databases are migrated automatically:

1. inspect `PRAGMA table_info(revisions)`;
2. add the column if it does not exist;
3. find legacy rows without a token;
4. canonicalize their stored JSON;
5. calculate and persist the SHA-256 token.

No historical revision is discarded.

## API identity

Revision-aware responses now expose tokens.

Important examples:

```json
{
  "revision": 2,
  "revision_token": "<sha256>"
}
```

Diff/review endpoints expose base/latest tokens where relevant.

## Status states

`GET /api/penpot/projects/{project_id}/status` accepts:

- `local_revision`
- `local_revision_token`

States are:

- `unknown` — no local revision supplied;
- `behind` — local numeric revision is older;
- `ahead` — local numeric revision is newer;
- `unverified` — numeric revision matches but Penpot has no fingerprint;
- `in_sync` — numeric revision and token both match;
- `diverged` — numeric revision matches but token differs.

The critical safety rule is:

```text
same revision number + different token != in sync
```

## Write protection

Penpot-originated writes now require both:

```json
{
  "expected_revision": 2,
  "expected_revision_token": "<sha256>"
}
```

If the number differs, the API returns a revision conflict.

If the number matches but the fingerprint differs, the API returns a `revision_diverged` conflict.

Missing fingerprint identity is rejected rather than treated as trusted legacy state.

## Base-sensitive reconciliation

Operations that depend on an earlier Penpot base revision require:

```json
{
  "from_revision": 2,
  "from_revision_token": "<sha256>"
}
```

This applies to flows such as:

- whole-document reconciliation;
- three-way review;
- property resolution;
- selective pull.

The server verifies that the supplied base token matches the stored content for that numeric revision before comparing anything.

## Penpot plugin

The plugin now stores:

```text
designbridge:revision
designbridge:revision-token
```

Context messages include both fields.

When Penpot receives a new verified revision from DesignBridge, it updates both values together.

Older Penpot files without a token become `unverified` until they pull/reconcile against the current canonical revision.

## Regression coverage

v0.18 includes tests for:

- deterministic token generation;
- token persistence in save/load/history;
- automatic migration/backfill of a legacy database;
- revision-number reuse producing a different token;
- `diverged` status for same-number/different-token state;
- `unverified` status when the token is missing;
- rejecting writes without a token;
- rejecting writes with a mismatched token;
- accepting writes with the correct revision identity.

## Next work

Once revision fingerprinting is merged and verified, DesignBridge can safely continue with richer Penpot-native variant integration and later structural synchronization without relying on ambiguous numeric revision identity.
