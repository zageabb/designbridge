# v0.19 Native Penpot variant integration

DesignBridge v0.19 connects canonical variant families to Penpot's native VariantComponent/VariantContainer model.

## Goal

v0.17 introduced canonical variant families and safe component-swap switching.

v0.19 adds a native path when the Penpot file already represents the same family as a native variant set.

The existing component-swap implementation remains the fallback.

## Penpot API used

The Penpot plugin API exposes:

- `LibraryComponent.isVariant()`;
- `LibraryVariantComponent.variantProps`;
- `LibraryVariantComponent.variants`;
- `Variants.id`;
- ordered `Variants.properties`;
- `Variants.variantComponents()`;
- component-copy `switchVariant(position, value)`;
- `waitForLayoutUpdate()`.

DesignBridge uses these APIs to inspect and switch native variants without detaching component copies.

## Native discovery

The plugin enumerates local and connected Penpot library components.

For each native variant family it records:

- Penpot native variant ID;
- library ID;
- ordered property names;
- DesignBridge variant-group tag, when exactly one group is represented;
- each member's Penpot component ID;
- each member's DesignBridge component ID;
- each member's canonical group tag;
- each member's native `variantProps`.

Discovery is read-only and does not change the active page or canvas.

## Canonical mapping

A Penpot native family is considered safe for native switching only when all of the following hold:

1. exactly one Penpot native family claims the canonical `variant_group`;
2. the native component membership matches the canonical component membership;
3. the native property-name set matches the canonical property-name set;
4. every tagged Penpot component's native property values equal the canonical component's `variant_properties`.

Possible mapping states:

- `in_sync`;
- `absent`;
- `mismatch`;
- `ambiguous`.

Anything other than `in_sync` uses the existing component-swap fallback.

## API

### Native mapping report

```text
POST /api/penpot/projects/{project_id}/native-variant-report
```

Request:

```json
{
  "native_variants": [
    {
      "native_variant_id": "penpot-variant-id",
      "library_id": "library-id",
      "property_names": ["state"],
      "designbridge_variant_group": "card-state",
      "components": [
        {
          "designbridge_component_id": "card",
          "variant_props": {"state": "default"}
        }
      ]
    }
  ]
}
```

The response includes the current revision fingerprint and the mapping report.

### Switch plan

The existing variant switch plan accepts the discovered native metadata:

```text
POST /api/penpot/projects/{project_id}/variant-switch-plan
```

The plan still performs the canonical v0.17 compatibility checks first.

It then returns one of two strategies.

Native:

```json
{
  "kind": "native_variant",
  "native_variant_id": "penpot-variant-id",
  "steps": [
    {"position": 0, "property": "state", "value": "active"}
  ]
}
```

Fallback:

```json
{
  "kind": "component_swap",
  "reason": "no verified native Penpot variant mapping"
}
```

## Native switching

When the approved strategy is `native_variant`, the plugin:

1. verifies the selected shape is still a component copy;
2. verifies its current library component is still a native variant;
3. verifies the Penpot native variant ID still matches the approved plan;
4. applies each changed property with `switchVariant(position, value)`;
5. waits for Penpot component/layout synchronization;
6. verifies the resulting component's DesignBridge ID equals the requested target;
7. reapplies the already-approved remapped DesignBridge overrides;
8. only then allows the existing canonical commit stage to proceed.

If native validation fails, the switch is rejected rather than silently changing strategy after approval.

## Fallback behavior

When no exact native mapping exists, DesignBridge continues to use the v0.17 guarded `swapComponent(...)` path.

This means existing DesignBridge variant families remain usable even when:

- Penpot components are not native variants;
- the native family is incomplete;
- Penpot property names differ;
- Penpot property values differ;
- multiple native families claim the same canonical group.

## Revision integrity

v0.18 revision fingerprints remain mandatory.

Variant planning returns the current revision token.

The UI will not execute the switch if the plan's revision number or token differs from the Penpot file's stored identity.

The canonical switch commit still requires both `expected_revision` and `expected_revision_token`.

## Current boundary

v0.19 does **not** automatically convert ordinary Penpot components into VariantContainers.

It also does not rewrite existing Penpot variant property definitions.

Those actions can restructure a design system and are intentionally deferred until discovery/mapping behavior is proven stable.

## Tests

Regression coverage includes:

- exact native family mapping;
- native property-value mismatch;
- ambiguous duplicate native family claims;
- ordered native property switch steps;
- component-swap fallback when native mapping is absent or mismatched;
- API native mapping report;
- API native switch strategy selection;
- revision-token propagation through planning.
